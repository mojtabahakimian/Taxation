# سرور تستی محلی سامانه مؤدیان

یک شبیه‌ساز کامل از API سامانه مؤدیان که روی همین کامپیوتر اجرا می‌شود.
بدون اینترنت، بدون کارپوشه، بدون دیتابیس.

## چرا؟

سندباکس واقعی برای تست اصلاحی پلکانی بی‌فایده است، چون خریداری وجود ندارد که
صورتحساب مرجع را تایید کند و تایید سیستمی ۳۰ روز طول می‌کشد. اینجا با یک
دستور، وضعیت هر صورتحساب را عوض می‌کنیم و بلافاصله تست می‌گیریم.

## اجرا

دو پنجره لازم است.

**پنجره ۱ — سرور:**

```bash
python TestTools/LocalMoadian/moadian_mock.py
```

**پنجره ۲ — تست‌ها:**

```bash
dotnet run --project TestTools/LocalMoadian
```

اگر سرور بالا نباشد، فقط تست‌های آفلاین (سریال، اعتبارسنجی خریدار، کد شعبه)
اجرا می‌شوند و بقیه رد می‌شوند.

پیش‌نیاز پایتون: `pip install cryptography`

## چه چیزی شبیه‌سازی می‌شود

پروتکل دقیقاً همان SDK نسخه 0.0.34 است — رمزنگاری واقعی انجام می‌شود:

```
aesKey        = ۳۲ بایت تصادفی
symmetricKey  = base64( RSA-OAEP-SHA256( hex(aesKey) ) )
iv            = hex(۱۶ بایت)
data          = base64( AES-GCM( xor(json, aesKey) ) )
```

سرور کلید عمومی خودش را از طریق `GET_SERVER_INFORMATION` به برنامه می‌دهد، بعد
با کلید خصوصی خودش بسته‌ها را باز می‌کند. یعنی اگر جایی در ساخت بسته اشکالی
باشد، اینجا هم دیده می‌شود.

### مسیرهای پیاده‌سازی‌شده

| مسیر | کار |
|---|---|
| `self-tsp/sync/GET_SERVER_INFORMATION` | زمان سرور + کلید عمومی |
| `self-tsp/sync/GET_TOKEN` | توکن ساختگی |
| `self-tsp/async/normal-enqueue` | دریافت و اعتبارسنجی صورتحساب |
| `self-tsp/sync/INQUIRY_BY_REFERENCE_NUMBER` | استعلام با کد رهگیری |
| `self-tsp/sync/INQUIRY_BY_UID` | استعلام با UID |

### قواعدی که کنترل می‌شوند

| کد | شرط |
|---|---|
| `0300101` | شماره مالیاتی تکراری یا با طول غلط |
| `0300601` | مرجع یافت نشد / مرجع تایید نشده / اصلاحی موازی |
| `0101204` | طول شماره اقتصادی خریدار (۱۴ حقیقی و اتباع، ۱۱ حقوقی و مشارکت) |
| `0101104` | طول شماره ملی (۱۰) یا کد فراگیر (۱۲) |
| `0101504` | کد شعبه غیر از ۴ رقم |
| `0200201` | تاریخ بیش از ۱۲ روز قدیمی یا در آینده |
| `0103705` | مجموع اقلام با مبلغ کل نمی‌خواند |
| `0300401` | نوع صورتحساب (inty) غیر از ۱ تا ۳ |
| `0300801` | موضوع صورتحساب (ins) غیر از ۱ تا ۴ |
| `0102804` | روش تسویه (setm) غیر از ۱ تا ۳ |
| `0102903` | مبلغ نقدی با روش تسویه نمی‌خواند |
| `0103003` | مبلغ نسیه با روش تسویه نمی‌خواند |
| `0103301` | شناسه کالا/خدمت نامعتبر |
| `1300501` | *هشدار* — سریال با مرجع فرق دارد (صورتحساب رد نمی‌شود) |

توجه: کدهایی که با `1` شروع می‌شوند هشدارند و مانع پذیرش نمی‌شوند — دقیقاً
مثل سامانه واقعی.

## کنترل دستی سرور

```bash
# دیدن همه صورتحساب‌های ثبت‌شده و ردشده
curl http://127.0.0.1:9090/__state

# تایید یک صورتحساب (نقش خریدار در کارپوشه)
curl -X POST http://127.0.0.1:9090/__set_status \
     -H "Content-Type: application/json" \
     -d '{"taxid":"A2HGPP05...","status":"CONFIRMED"}'

# پاک کردن همه چیز
curl -X POST http://127.0.0.1:9090/__reset -d '{}'
```

وضعیت‌های معتبر: `IN_PROGRESS`، `CONFIRMED`، `SYSTEM_CONFIRMED`،
`NO_REACTION_NEEDED`، `REJECTED`، `CANCELLED`.

## وصل کردن خود برنامه به سرور محلی

در تنظیمات برنامه، آدرس سامانه را بگذارید:


و شناسه حافظه را `A2HGPP`. کلید خصوصی داخل `test_private_key.txt` است.
**این کلید فقط برای تست است — هرگز روی سامانه واقعی استفاده نشود.**

### مهم‌ترین نتیجه — اصلاحی پلکانی

```
اصلی → تایید → اصلاحی۱ → تایید → اصلاحی۲ → تایید → اصلاحی۳   ✅
اصلی → اصلاحی۱ (مرجع تایید نشده)                             ❌ 0300601
اصلی(تایید) → اصلاحی۱ + اصلاحی۲ موازی                        ❌ 0300601
اصلاحی۲(تایید) ... بازگشت به مرجع اول                        ❌ 0300601
```

### نتیجه دوم — سریال اصلاحی

```
اصلاحی با همان سریال مرجع    ✅ پذیرفته، بدون هیچ هشداری
اصلاحی با سریال متفاوت       ✅ پذیرفته، فقط هشدار 1300501
```

یعنی هشداری که قبلا برای «سریال تکراری» گذاشته بودم بی‌مورد بود و درست شد که
برداشته شد.

### نتیجه سوم — ماتریس موضوع × روش تسویه

هر چهار موضوع در هر سه روش تسویه تست شد، ۱۲ ترکیب، همه پذیرفته:

|  | نقدی | نسیه | نقدی/نسیه |
|---|---|---|---|
| اصلی | ✅ | ✅ | ✅ |
| اصلاحی | ✅ | ✅ | ✅ |
| ابطالی | ✅ | ✅ | ✅ |
| برگشتی | ✅ | ✅ | ✅ |

به‌علاوه صورتحساب نوع دوم با هر سه روش تسویه.

### یک نکته در مورد setm

`CalculateCapInsp` برای نقدی `cap = tbill` (شامل مالیات) می‌گذارد و برای نسیه
`insp = tbill`. طبق جدول‌های ۲۵ و ۲۶ فرمول `tbill - tvam - todam` است، ولی خود
کد در توضیحاتش نوشته که سامانه در عمل مقدار کل را برای نقدی و نسیه می‌پذیرد.
سرور ساختگی هم همین رفتار را دنبال می‌کند، پس این تست‌ها **رفتار فعلی برنامه را
تثبیت می‌کنند، نه اینکه آن را با سند بسنجند**. فرمول کامل فقط در حالت نقدی/نسیه
اعمال و تست می‌شود.

## گروه ۱۶ — ارسال گروهی سنگین

این گروه مسیر واقعی `SendInvoiceBulk` را روی دیتابیس واقعی اجرا می‌کند.

```bash
sqlcmd -S "MERCEDES\SQL2022" -E -C -I -i TestTools/LocalMoadian/seed_bulk_test.sql
dotnet run --project TestTools/LocalMoadian -- --bulk
sqlcmd -S "MERCEDES\SQL2022" -E -C -I -i TestTools/LocalMoadian/cleanup_bulk_test.sql
```

شرایط تست: ۱۲۰ فاکتور با شماره ۱۰۰۰۰۰۱ تا ۱۰۰۰۱۲۰، جدول TAXDTL خالی،
بسته‌بندی ۹۹تایی (یعنی دو بسته).

### نسخه SDK

پروژه به **0.0.34** لینک شده (بستهٔ NuGet). سورس‌های روی دسکتاپ قدیمی‌ترند:

| نسخه | Insr | Nti1/Nti2 | آدرس INQUIRY_BY_TIME_RANGE |
|---|---|---|---|
| 0.0.27 (سورس) | ندارد | ندارد | غلط — به GET_SERVICE_STUFF_LIST می‌رفت |
| 0.0.30 (سورس) | `string?` | دارد | غلط |
| **0.0.34 (در پروژه)** | **`int?`** | دارد | درست |

یعنی سورس ۰.۰.۳۰ ارتقا نیست، عقب‌گرد است. مسیرهای API و رمزنگاری در هر سه
یکسان‌اند، پس سرور ساختگی با هر سه کار می‌کند. گروه ۱۷ این را هر بار دوباره
می‌سنجد، پس اگر روزی نسخه عوض شد و قراردادی شکست، تست قرمز می‌شود.

## نکته‌ای که موقع ساخت داده تستی پیدا شد

`dbo.HEAD_BACK_ANBAR` یک VIEW است روی HEAD_LST با `TAG - 11 AS HTAG`.
مسیر ارسال گروهی از همین view می‌خواند، پس:

```
HEAD_LST.TAG = 13   →   HTAG = 2   →   SendAsync(..., 2, ...)
```

بنابراین «۱۳ در گرید» و «۲ در ارسال» با هم متناقض نیستند. ولی کوئری محافظِ
«قبلاً ارسال شده» در `Prg_Grpsend/MainWindow.xaml.cs` همان `13` را روی TAXDTL
می‌زند، در حالی که TAXDTL مقدار `2` را ذخیره می‌کند. این تست ثابت کرد
`TAXDTL.TAG` همیشه برابر tag ارسالی است، نه tag سرصفحه.
