# سرور تستی محلی سامانه مؤدیان

یک شبیه‌ساز کامل از API سامانه مؤدیان که روی همین کامپیوتر اجرا می‌شود.
بدون اینترنت، بدون کارپوشه، بدون دیتابیس.

## چرا؟

سندباکس واقعی برای تست اصلاحی پلکانی بی‌فایده است، چون خریداری وجود ندارد که
صورتحساب مرجع را تایید کند و تایید سیستمی ۳۰ روز طول می‌کشد. اینجا با یک
دستور، وضعیت هر صورتحساب را عوض می‌کنیم و بلافاصله تست می‌گیریم.

## اجرا

دو پنجره لازم است.

**پنجره ۱ — سرور:**

```bash
python TestTools/LocalMoadian/moadian_mock.py
```

**پنجره ۲ — تست‌ها:**

```bash
dotnet run --project TestTools/LocalMoadian
```

اگر سرور بالا نباشد، فقط تست‌های آفلاین (سریال، اعتبارسنجی خریدار، کد شعبه)
اجرا می‌شوند و بقیه رد می‌شوند.

پیش‌نیاز پایتون: `pip install cryptography`

## چه چیزی شبیه‌سازی می‌شود

پروتکل دقیقاً همان SDK نسخه 0.0.34 است — رمزنگاری واقعی انجام می‌شود:

```
aesKey        = ۳۲ بایت تصادفی
symmetricKey  = base64( RSA-OAEP-SHA256( hex(aesKey) ) )
iv            = hex(۱۶ بایت)
data          = base64( AES-GCM( xor(json, aesKey) ) )
```

سرور کلید عمومی خودش را از طریق `GET_SERVER_INFORMATION` به برنامه می‌دهد، بعد
با کلید خصوصی خودش بسته‌ها را باز می‌کند. یعنی اگر جایی در ساخت بسته اشکالی
باشد، اینجا هم دیده می‌شود.

### مسیرهای پیاده‌سازی‌شده

| مسیر | کار |
|---|---|
| `self-tsp/sync/GET_SERVER_INFORMATION` | زمان سرور + کلید عمومی |
| `self-tsp/sync/GET_TOKEN` | توکن ساختگی |
| `self-tsp/async/normal-enqueue` | دریافت و اعتبارسنجی صورتحساب |
| `self-tsp/sync/INQUIRY_BY_REFERENCE_NUMBER` | استعلام با کد رهگیری |
| `self-tsp/sync/INQUIRY_BY_UID` | استعلام با UID |

## کنترل دستی سرور

```bash
# دیدن همه صورتحساب‌های ثبت‌شده و ردشده
curl http://127.0.0.1:9090/__state

# تایید یک صورتحساب (نقش خریدار در کارپوشه)
curl -X POST http://127.0.0.1:9090/__set_status \
     -H "Content-Type: application/json" \
     -d '{"taxid":"A2HGPP05...","status":"CONFIRMED"}'

# پاک کردن همه چیز
curl -X POST http://127.0.0.1:9090/__reset -d '{}'
```

وضعیت‌های معتبر: `IN_PROGRESS`، `CONFIRMED`، `SYSTEM_CONFIRMED`،
`NO_REACTION_NEEDED`، `REJECTED`، `CANCELLED`.

### یک نکته در مورد setm

`CalculateCapInsp` برای نقدی `cap = tbill` (شامل مالیات) می‌گذارد و برای نسیه
`insp = tbill`. طبق جدول‌های ۲۵ و ۲۶ فرمول `tbill - tvam - todam` است، ولی خود
کد در توضیحاتش نوشته که سامانه در عمل مقدار کل را برای نقدی و نسیه می‌پذیرد.
سرور ساختگی هم همین رفتار را دنبال می‌کند، پس این تست‌ها **رفتار فعلی برنامه را
تثبیت می‌کنند، نه اینکه آن را با سند بسنجند**. فرمول کامل فقط در حالت نقدی/نسیه
اعمال و تست می‌شود.

## نکته‌ای که موقع ساخت داده تستی پیدا شد

`dbo.HEAD_BACK_ANBAR` یک VIEW است روی HEAD_LST با `TAG - 11 AS HTAG`.
مسیر ارسال گروهی از همین view می‌خواند، پس:

```
HEAD_LST.TAG = 13   →   HTAG = 2   →   SendAsync(..., 2, ...)
```

بنابراین «۱۳ در گرید» و «۲ در ارسال» با هم متناقض نیستند. ولی کوئری محافظِ
«قبلاً ارسال شده» در `Prg_Grpsend/MainWindow.xaml.cs` همان `13` را روی TAXDTL
می‌زند، در حالی که TAXDTL مقدار `2` را ذخیره می‌کند. این تست ثابت کرد
`TAXDTL.TAG` همیشه برابر tag ارسالی است، نه tag سرصفحه.

## گروه ۲۸ — چرخهٔ کامل صورتحساب روی «سرور کامل»

سرور دوم: `moadian_mock_full.py` (پورت پیش‌فرض ۹۱۹۰). همان پروتکل سرور اول، به‌علاوه:

- **کارپوشه:** وضعیت‌های رسمی API نسخه ۲ (`AWAITING_REACTION`، `APPROVED`، `REJECTED`،
  `SYSTEMIC_APPROVED`، `NO_NEED_REACTION`، `IMPOSSIBLE_REACTION`، `CANCELED`)، تایید/رد
  خریدار، تایید سیستمی پس از ۳۰ روز، و باطل شدن مرجع وقتی ارجاعی‌اش تایید شد.
- **کدهای خطا از ساختار ۷ رقمی سند EC_V02** (رقم اول خطا/هشدار، دوم نوع اعتبارسنجی،
  سه رقم شمارهٔ فیلد، دو رقم جزئیات). هر پیام یک برچسب `source` دارد؛ قاعده‌هایی که
  عیناً در سند نیستند `derived` خورده‌اند. فهرست قواعد و ابهام‌ها: `GET __rules`.
- کنترل برای تست: `__buyer_action`، `__advance_days`، `__invoice_status`، `__config`، `__clock`.

خودآزمون سرور: `python3 TestTools/LocalMoadian/test_mock_full.py` (۸۷ تست؛ اگر قاعده‌ای
هرگز فعال نشود شکست می‌دهد).

`Lifecycle.cs` (گروه ۲۸) فقط با `--full=URL` اجرا می‌شود. مبالغ را کد تولید می‌سازد
(`CorrectionMath.RecalculateRow`، `CalculateCapInsp` مسیر گروهی) و ارسال با
`TaxService.SendInvoices` است. پوشش: اصلی (نوع × تسویه × نوع شخص)، اصلاحی/ابطالی/برگشتی
روی مرجع در هر وضعیت کارپوشه، زنجیرهٔ ارجاعی روی ارجاعی، قواعد برگشت از فروش، یک‌بار
مصرف بودن مرجع، مهلت ۱۲ روزه و ساعت جلوتر از سرور (02002)، cap/insp، هشدارِ غیرمسدودکننده،
ارسال مجدد با همان taxid، و دو واگرایی ثبت‌شده به عنوان دیده‌بان.

⚠️ **قید:** این سرور هم از روی اسناد نوشته شده. سبز بودن گروه ۲۸ یعنی کد تولید با
*خوانش ما از اسناد* می‌خواند، نه با سامانهٔ واقعی. خانه‌هایی که سند دوپهلوست assert
نمی‌شوند و در انتهای اجرا زیر «ابهام‌ها» چاپ می‌شوند.

**خرابکاریِ سنجیده‌شده روی کد تولید** (هر بار با `git checkout` برگردانده شد):

| خرابکاری | نتیجه |

## گروه ۲۹ — سر تا ته مسیرهای واقعی با دیتابیس ساختگی

کرده. پس `CL_CCNNMANAGER` و Dapper واقعی‌اند. هر SQL با regex شناسایی می‌شود؛ شکل
ناشناخته **استثنای بلند** می‌دهد و در `FakeDb.Errors` هم می‌ماند (چون کد تولید چند جا
استثنای دیتابیس را می‌بلعد)؛ هر نوشتن با پارامترهایش در ژورنال ثبت می‌شود. فهرست همهٔ
شکل‌های SQL دیده‌شده در پایان اجرا چاپ می‌شود.

⚠️ **حدود صادقانه:**
- این منطقِ C# دور دیتابیس را می‌سنجد، **نه خود SQL را**. نام/نوع ستون‌ها، JOIN های ویوی
  `DRVD_TBL` (و HEAD_BACK_ANBAR با TAG-11)، collation — این‌ها فقط با ‎`-Full`‎ روی SQL
  Server واقعی سنجیده می‌شوند. ردیف‌های `DRVD_TBL` خروجی ویو هستند که دستی ساخته شده‌اند.
- طرح TAXDTL از `FULL_TAXDTL` + DDL ِ `CL_ScriptUpdateDB.cs` است. نقض‌های NOT NULL آن DDL
  فقط **گزارش** می‌شوند (بعضی قطعاً با دیتابیس‌های زنده نمی‌خوانند، مثلاً `Indatim`).
- سرور کامل را خودمان از روی اسناد نوشته‌ایم؛ «پذیرفته شد» یعنی با خوانش ما از سند می‌خواند.
- `Thread.Sleep(10_000)` ِ مسیر تکی در زمان اجرا صفر می‌شود (`MOADIAN_E2E_REAL_SLEEP=1` خاموشش می‌کند).
- از `WIN_MODIFYINVOICE` هیچ خطی اجرا نمی‌شود (UI، و درج TAXDTL اش با `SqlConnection` خام و
  تراکنش است). از `MainWindow` پیگیری فقط حلقهٔ ارسال مجدد؛ دیالوگ‌ها، لاگ AMALIAT، تایمر و
  برچسب EXPIRED اجرا نمی‌شوند.

«یافته»ها رفتار **فعلی** را قفل می‌کنند (نه درست را): اگر کسی اصلاحشان کند قرمز می‌شوند و
باید آگاهانه به‌روز شوند.
